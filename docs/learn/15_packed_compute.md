# 15. Packed instructions: eight numbers per instruction

Most of the work in a game, a video player or a small neural network is one loop: the same small operation on
thousands of small numbers. A pixel channel is one byte, an audio sample is 16 bits, an int8 network's weights
are signed bytes. A 64-bit register can hold eight of those bytes, but `add` treats it as one number. This
chapter adds nine instructions that treat a register as eight bytes (or four 16-bit numbers) side by side, and
measures what they buy. The full design and every number are in [XCOMPUTE.md](../XCOMPUTE.md).

## Lanes

```text
          lane 7  lane 6  lane 5  lane 4  lane 3  lane 2  lane 1  lane 0
rs1        f0      10      80      7f      ff      01      c8      20
rs2        20      10      90      01      01      fe      64      10
paddus.b   ff      20      ff      80      ff      ff      ff      30
```

`paddus.b` adds each pair of bytes on its own. Two things differ from `add`:

* **No carry crosses a lane.** `0x7f + 0x01` is `0x80` in lane 4, and lane 5 never hears about it. In hardware
  this is eight 9-bit adders instead of one 64-bit adder: shorter, so faster.
* **It saturates.** `0xf0 + 0x20` is 272, which does not fit in a byte. A plain add would wrap to `0x10`, and a
  bright pixel would turn nearly black. `paddus.b` stops at 255 (`0xff`): the pixel stays white. The `us` in
  the name means "unsigned, saturating".

This is called SIMD (single instruction, multiple data). Doing it inside the ordinary registers is called
SWAR (SIMD within a register). Intel's MMX did the same in 1997, with instructions called `PADDUSB`, `PAVGB` and
`PSADBW`.

## Reductions: many lanes into one number

Some loops do not produce eight results, they add everything up:

* `psad.b` sums the eight absolute differences `|a - b|`. A video encoder compares a block of the new frame with
  candidate blocks of the old one and keeps the closest (motion search). That is millions of `|a - b|`.
* `pdot.b` sums the eight products `a * b` of signed bytes. One neuron of an int8 network is a long dot product
  of its weights and its inputs.
* `pdot.h` does the same for four 16-bit numbers, and `pmulhrs.h` multiplies four Q15 fixed-point numbers.

Q15 is how small chips do fractions without floating point: the 16-bit number `n` stands for `n / 32768`.
`16384` is 0.5, `-32768` is -1. `pmulhrs.h` multiplies two of them, rounds and shifts back to Q15: 0.5 x 0.5 is
`(16384 x 16384 + 0x4000) >> 15 = 8192`, which is 0.25.

## Too much for one stage: split it

Eight multiplies and an eight-way sum is too much logic for one clock period. Sixfold already had the answer
from `hamming` ([chapter 11](11_custom_instructions.md)): split the work across two stages.

```text
EXECUTE   CustomPrepare: the 8 products (each a carry-save tree)  ->  MEMORY_CUSTOM_PREPARED (272 bits)
MEMORY    CustomUnit:    the sum of the 8 products, then one add  ->  WRITEBACK
```

Look at [`src/Custom_Unit.sv`](../../src/Custom_Unit.sv) (generated by `make custom`): `f_pdotb_prep` is the
first half and `f_pdotb_fin` the second. The register between them, `MEMORY_CUSTOM_PREPARED` in
[`src/Riscv64.sv`](../../src/Riscv64.sv), is 272 bits wide, because the 16-bit products of `pdot.h` were still
too slow and cross the boundary in carry-save form: two numbers per product that have not been added yet.

A carry-save adder is the trick behind every fast multiplier: three numbers go in, two come out, and no carry
runs along the word. Eight numbers become two in four layers, and only the very last addition waits for a
carry.

## What it buys

| kernel | speedup (performance build) |
|---|---:|
| brighten 2048 bytes (`paddus.b`) | 10.8x |
| blend 2048 bytes (`pavgu.b`) | 10.4x |
| motion search (`psad.b`) | 15.1x |
| int8 layer (`pdot.b`) | 19.6x |
| 4 x 4 matrix on 256 vertices (`pdot.h`) | 10.5x |
| audio gain (`pmulhrs.h`) | 13.5x |

Each program runs a plain version and a packed version and checks they agree. More than 8x on eight lanes?
The plain loops spend a compare and a branch per element, and the plain multiply waits for the iterative
multiply unit; the packed loop does neither. The clock did not get slower, but the custom unit is now as slow
as the ALU: the next, deeper instruction would cost clock.

## Turning it off

The nine instructions are a group, `xcompute`, behind the parameter `XCOMPUTE` of `Riscv64`. It is off by
default, so a design that uses Sixfold as a part keeps its exact behavior; every build in this repository turns
it on. With it off, the encodings write 0, and `tests/xcompute_off.s` checks that.

## Run it

```bash
make run PROG=27_int8_dot
make compute-bench
node tools/test.mjs --config=xoff
```
